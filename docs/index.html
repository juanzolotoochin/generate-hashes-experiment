How --experimental_generate_hashes works

A design overview for reviewers of the pull request. It explains what the flag computes, how the code is organized, and the choices behind it. No knowledge of Bazel's internals is assumed; the Skyframe background is in a section you can skip.

Pull request · Branch · Benchmark results

1 · Overview

What the feature does

CI systems often decide which targets a change affects by hashing every target together with its transitive inputs on two commits and comparing the hashes. Tools that do this today work from outside Bazel. bazel-diff rebuilds Bazel's view of the graph from query output, which misses inputs such as toolchains. target-determinator runs a full analysis, which is slow and fetches every toolchain.

This change moves the hashing into Bazel. bazel query --experimental_generate_hashes prints each target in the result followed by a hash of the target and everything it transitively depends on.

In short. New SkyFunctions compute a direct hash for each target: its attributes, its rule definition, and the content of its source files. Because they live in Skyframe, a warm server only recomputes what changed. A plain Java pass then walks the dependency graph and combines direct hashes bottom-up, handling cycles with Tarjan's algorithm.

Fetched external repos are hashed as one unit per fetch rather than file by file. Each toolchain_type depends on every toolchain registered for it, and toolchains in external repos are hashed by their repo definitions without fetching them. A cquery variant hashes the configured graph instead.

2 · From the user's side

Using it

$ bazel query --experimental_generate_hashes 'deps(//app:server, 1)'
//app:server 9c1e5a0f3b…e71d          # 64 hex characters in real output
//app:main.go 41aa07c2d8…09b3
@com_github_foo//:foo 7d52e1b9a4…c6f0

$ bazel cquery --experimental_generate_hashes //app:server
//app:server (3f2b1c0) 5be0a93c71…2d4e

With the flag, --output is ignored and each line is <label> <hash> (cquery adds the configuration). Any query expression works; a typical CI run hashes //... on the base and head commits and builds the targets whose hashes differ.

querycquery
Graph hashedUnconfigured target graphConfigured target graph
select()All branches countOnly the branch taken
ToolchainsEvery toolchain registered for each type usedThe toolchain actually resolved
Build optionsNot part of the hashPart of every hash

The two modes are complementary. query over-approximates: anything that may affect a target in some configuration changes its hash, which is safe and cheap. cquery is precise for one set of build options, at the cost of analysis.

Flags that would drop dependencies from the hash are rejected: --noimplicit_deps, --notool_deps, and for query, --aspect_deps other than conservative. The flag is also rejected inside genquery.

A dependency that doesn't exist is hashed as missing, so creating it later changes its dependents' hashes. Any other error is reported and fails the command, because the hashes of targets that depend on a broken target can't be trusted.

3 · Background

Skyframe background

The design leans on Skyframe, Bazel's incremental evaluation engine. If you already know it, skip to section 4.

Skyframe in five minutes

The Bazel server is a long-lived Java process that keeps an in-memory graph of everything it has computed. Almost everything Bazel does (reading files, loading packages, analysing rules) is a node in that graph.

SkyKeyThe name of a piece of work: "the file app/main.go", "the package //app".
SkyValueIts immutable result, compared with equals().
SkyFunctionCode that turns a key into a value, possibly asking for other keys.
  1. Memoization. A computed value stays in memory, and the next command that asks for it gets it for free.
  2. Invalidation. Skyframe records which keys each function asked for. Between commands, Bazel marks nodes for changed files dirty, and everything that depends on them is re-checked.
  3. Change pruning. If a dirty node recomputes to a value equal to the old one, its dependents aren't recomputed.

Two constraints shape this design. A SkyFunction that needs a value that isn't ready returns null, and Skyframe calls it again from the top once the value is computed. And the graph of SkyKeys must be acyclic.

Existing nodes this feature uses: FileValue (a file's metadata, with symlinks resolved, and a content digest when the filesystem offers one cheaply), PackageValue (a loaded BUILD file), RepositoryDirectoryValue ("this external repo has been fetched", recomputed on refetch) and RepoDefinitionValue (the repo rule and attributes that define an external repo, available without fetching it).

4 · Code layout

Architecture

The work is split between Skyframe functions, which compute per-target facts and are memoized, and a plain Java pass that combines them along the graph. Everything new for query is in lib/query2/query/hash/.

PieceKindRole
DirectTargetHashFunctionSkyFunctionGiven a label: the target's direct hash and the sorted labels of its dependencies.
SourceFileDigestFunctionSkyFunctionGiven a path: content digest and executable bit of one source file.
RepoContentDigestFunctionSkyFunctionGiven an external repo: one digest of all its files, or "hash file by file" for repos that can change without a refetch.
RegisteredToolchainsByTypeFunctionSkyFunctionThe toolchains registered in MODULE.bazel files, grouped by toolchain_type.
TransitiveHashesPlain JavaBreadth-first walk that collects direct hashes, then Tarjan-based combination into transitive hashes.
HashesOutputFormatterCallbackcquery formatterThe cquery variant: walks the configured graph and reuses the direct hashes and the combine step.

Why the transitive hash isn't a SkyFunction

The natural design would have each target's SkyFunction request its dependencies' hashes. That doesn't work, because the unconfigured target graph can contain cycles: for example, a toolchain whose tools depend on something that uses the toolchain. In a build, configuration transitions break such cycles, but query sees them, and Skyframe forbids cycles between keys.

So DirectTargetHashFunction never requests another target's hash. It returns only the labels of the dependencies, and TransitiveHashes does the combining. The expensive parts (package loading, file digests) stay memoized; the combine step is linear in the size of the graph.

The functions are registered in BuiltinCommandModule.workspaceInit. QueryCommand collects the query result instead of streaming it, then calls TransitiveHashes.compute with an evaluator backed by SkyframeExecutor.prepareAndGet and the --loading_phase_threads parallelism.

5 · DirectTargetHashFunction

A target's own hash

A direct hash covers everything about a target except its dependencies' contents. Every direct hash starts with the target's canonical label and its kind (go_binary, source file, …).

TargetAlso hashed
RuleEvery attribute value, plus the digest of the rule's definition environment (the .bzl file that defines it and everything that file loads). This reuses SyntheticAttributeHashCalculator, the code behind query --output=proto's rule hashes, so formatting and comments in BUILD files don't matter.
Source fileIts content digest and executable bit, or the digest of its whole repo (section 6).
package_groupThe packages it contains.
toolchain()For each implementation in a fetched external repo, a digest of that repo's definition (section 7).

Repo rules often write absolute paths into the BUILD files they generate, for instance in the error message of a toolchain that can't be configured on this host. String attributes containing the output base or the workspace path are hashed with those paths replaced by <output_base> and <workspace>, so hashes don't depend on where those directories are.

Which dependencies are followed

  • All label attributes except "nodep" ones such as visibility, using the same visitor as query deps().
  • Toolchain types of the default exec group, and of every declared exec group.
  • For rules with aspects attached to their attributes: the label dependencies and toolchain types of every aspect that may apply, as --aspect_deps=conservative does.
  • For toolchain(): the select() keys of its toolchain attribute, and implementations that can't be hashed by repo definition.
  • For toolchain_type: the toolchains registered for it, added by TransitiveHashes (section 7).

Dependencies are sorted, so attribute order and visitation order don't affect the hash.

6 · Files

Source files and external repos

Source files are hashed one of two ways, chosen per repo by RepoContentDigestFunction.

RepoHow its files are hashedWhy
Main repo; local and configure repo rules; overridden repos; repos that failed to fetchFile by file, through SourceFileDigestFunctionTheir files can change without Bazel refetching anything, so each file must be tracked.
Every other external repoOne digest of the whole repo, through RepoContentDigestFunctionTheir contents only change when Bazel refetches them, and a refetch invalidates RepositoryDirectoryValue.

File by file

SourceFileDigestFunction depends only on the file's FileValue, so it reruns exactly when Skyframe sees the file change. It uses the digest in the FileValue when the filesystem provides one, and otherwise reads the file through Bazel's digest cache. It also records the executable bit, which changes a target's outputs when the file is a runfile. Missing files, directories and special files hash as fixed markers; a directory used as a source label isn't walked.

Whole-repo digest

Toolchain and SDK repos can hold hundreds of thousands of files. Tracking each in Skyframe would mean checking all of them for changes on every command. Instead, RepoContentDigestFunction reads the repo once per fetch with direct filesystem calls: it lists directories recursively in sorted order without following symlinks, and fingerprints each entry's relative path, type, and file digest or symlink target. Because it reads files outside Skyframe, it is registered as non-hermetic.

In such a repo, a source file's direct hash uses the repo digest instead of its own content. A rule's dependencies on files in its own package are dropped from the walk and the repo digest goes into the rule's hash instead, which keeps the walk from visiting every file of large repos.

Two details keep the digest stable across machines:

  • Symlinks. Repo rules often create absolute symlinks into the output base or the workspace. Targets under the repo, external/, the workspace or the output base are hashed relative to them. A symlink into the workspace is also hashed by the content of the file it points to, because editing that file triggers a refetch without changing the symlink.
  • Executable bits are left out, because a locally fetched repo and one served from the remote repo contents cache report them differently.

Repos from the remote repo contents cache

With --experimental_remote_repo_contents_cache, a cache hit gives Bazel a repo's directory listing and file digests without the file contents, served through an in-memory overlay filesystem. That overlay's getDigest() returns the stored digest instead of downloading the file (RemoteExternalOverlayFileSystem.java:944-950), and it uses the native filesystem's digest function. So the repo digest is computed without downloading anything and matches a local fetch of the same repo. When the cache drops files, the overlay invalidates the repo's RepositoryDirectoryValue, and the digest is recomputed on the next command.

7 · Toolchains

Toolchains

Toolchains are the main input that hashing from outside Bazel misses: a rule names a toolchain_type, and which toolchain() implements it is only decided during analysis, by toolchain resolution, which needs a configuration. query has no configuration, so it over-approximates.

  1. Every registered toolchain counts. RegisteredToolchainsByTypeFunction expands the register_toolchains patterns of all modules and groups the toolchain() targets by their toolchain_type, which is a non-configurable attribute, so loading is enough. TransitiveHashes adds an edge from each toolchain_type to all of them. A toolchain whose package fails to load counts for every type.
  2. Implementations are hashed by definition. A toolchain() points at its implementation through a nodep attribute, usually in an external repo with a compiler or SDK for one platform. Following it would fetch an SDK for every platform. Instead, the toolchain's direct hash includes a digest of that repo's definition (repo rule, the transitive digest of its .bzl files, attribute values) and of every repo it can see or that its label attributes point to. Files those label attributes point to in the main repo or in local repos, such as patches, are hashed by content.
  3. Fallback. If the implementation lives in the main repo or in a repo that can change without its definition changing (local, configure, overridden), it is followed as a normal dependency.

The result: a change to any registered toolchain for a type changes every target that uses the type, and query never fetches toolchain repos it doesn't otherwise load. For repo rules that download checksummed archives, the definition determines the contents, so nothing is lost.

8 · TransitiveHashes

Combining hashes

  1. Walk. Starting from the query result, request the direct hashes of the current level as one parallel Skyframe evaluation, with keep-going. Unseen dependency labels form the next level. Progress shows as Hashing: visited N targets (depth D, P pending).
  2. Find cycles. Run Tarjan's strongly-connected-components algorithm over the collected graph, with an explicit stack to avoid overflowing on deep graphs. Components come out leaves first.
  3. Hash. A target not in a cycle gets H(direct hash, [(dep label, dep hash) …]). The members of a cycle share one hash over all their direct hashes and edges, then each member's hash is that shared hash salted with its own label.

A dependency that could not be loaded because it doesn't exist contributes its label and a <missing> marker, so a dependent's hash changes when the target is created. Any other failure is collected as an error. Hashes that could be computed are still printed, but the command fails with "hashes of targets depending on them may be wrong".

The combine function is generic over the node type, which lets the cquery mode reuse it with configured targets as nodes.

9 · Configured graph

The cquery mode

cquery --experimental_generate_hashes uses a separate output formatter, HashesOutputFormatterCallback, that:

  1. Walks the configured graph breadth-first from the result, using cquery's own dependency lookup. That includes resolved toolchains, execution platforms and aspect dependencies, and only the select() branches taken.
  2. Gets each node's unconfigured direct hash from DirectTargetHashFunction, so file and repo digests are shared with query mode and memoized, and combines it with the node's configuration checksum and, for aspects, the aspect description.
  3. Names each node by label plus configuration checksum, and combines with the same Tarjan function.

Because the configuration checksum covers all build options, changing any option rehashes every target in that configuration. Changes reachable only through untaken select() branches or unselected toolchains don't change hashes. The hashes are only comparable between runs with the same options.

10 · Incrementality

Warm server behavior

The walk and combine step always run, but they only read memoized values. Which per-target work reruns after a change:

ChangeRecomputed
Source file in the main repoThat file's SourceFileDigestFunction and direct hash
BUILD fileDirect hashes of targets in that package; unchanged targets prune
.bzl filePackages that load it, and direct hashes of rules defined in it
External repo refetchedThat repo's digest; an identical refetch prunes there
register_toolchains in MODULE.bazelRegisteredToolchainsByTypeFunction
NothingNo per-target work

A file whose mode changes but whose content doesn't is only noticed when Bazel tracks that file by ctime, which is the default for local files.

11 · Known gaps

What isn't covered

Two targets with equal hashes are expected to build the same, given the same Bazel version, build options and host. These inputs are not part of the query hash:

Not seenWhy
Build options, --extra_toolchainsPart of the configuration. Covered by cquery mode.
Hand edits inside a fetched external repo that don't trigger a refetchThe whole-repo digest is computed once per fetch.
Contents of a directory used as a source label, in the main repo or local reposNot walked; hashed as <directory>. In fetched repos they are covered by the repo digest.
Output base path, for a fetched repo that writes its own absolute path into a fileThe repo is hashed by its file contents, and the path is part of them, so moving the output base changes its dependents' hashes (1 of 46 targets in the benchmark). Absolute symlinks and paths in rule attributes are handled.
Executable bits in fetched reposLeft out so that remote cache hits and local fetches agree.
Changes to visible repos that are local, configure or overridden, when reached only through a toolchain's repo definitionThose repos are skipped in the definition digest, except for files that repo rule attributes point to.
The Bazel version and built-in rule implementationsCompare hashes only between runs of the same Bazel binary.

Benchmark

The hashbench benchmark compares both modes with bazel-diff and target-determinator on a workspace with Go, Python, Rust and C++ targets and real toolchain repos, across 47 change scenarios. Its findings are in FINDINGS.md.

  • Remote repo contents cache. Every scenario was run with --experimental_remote_repo_contents_cache off and on, with identical results. The determinism suite also checks that hashes don't change when the cache is turned on or off, when the flag is toggled in the same output base, and when a build materializes cached repos between two snapshots.
  • Determinism. The same revision hashed twice gives identical hashes across a server restart, another user and home directory, a fresh output base, another checkout path and fresh caches. The one difference found is listed in section 11.

Bazel's own test suite doesn't combine the flag with the remote repo contents cache yet. src/test/py/bazel/bzlmod/remote_repo_contents_cache_test.py would be the place for one.
