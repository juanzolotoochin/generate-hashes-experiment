How query --experimental_generate_hashes handles remote repos

A guided tour for someone who knows Bazel well from the command line but hasn't read its source. It covers what the new flag computes, the Bazel internals it is built on, and why files from --experimental_remote_repo_contents_cache get hashed correctly without being downloaded.

1 · The short answer
Yes, remote repos are handled correctly.

A repo served from the remote repo contents cache comes from a reproducible repo rule, so --experimental_generate_hashes hashes it as one unit: it lists the repo and asks for the digest of every file. The cache already stores those digests, and the overlay filesystem returns them without downloading the file bytes.

The digests are the ones Bazel would compute from the files on disk, and executable bits are left out of the repo digest. So a target hashes the same whether its repo came from the cache or was fetched locally.

This conclusion comes from reading the code. No end-to-end test covers this combination yet (see section 9).

The rest of this page explains why, starting from the parts of Bazel you've only seen from the outside.

2 · From the user's side

What the flag does

Normally bazel query prints the targets that match your expression. With --experimental_generate_hashes it ignores --output and prints each target followed by a SHA-256 fingerprint of that target and everything it depends on:

$ bazel query --experimental_generate_hashes 'deps(//app:server, 1)'
//app:server 9c1e5a0f3b…e71d   # 64 hex characters in real output
//app:main.go 41aa07c2d8…09b3
@com_github_foo//:foo 7d52e1b9a4…c6f0

If anything in a target's transitive closure changes, its hash changes. That makes it useful for "which targets are affected by this commit?" tooling: hash every target on two commits and compare.

Each hash covers:

  • the target's label and kind (go_binary, source file, …);
  • for rules: every attribute value, plus a digest of the rule's Starlark definition and the .bzl files it was loaded from. Absolute paths to the output base or the workspace inside string attributes are replaced by placeholders, so hashes don't depend on where those directories are;
  • for source files in the main repo and in local or configure repos: the file's content digest and its executable bit;
  • for source files in other external repos: one digest of the whole repo's contents (see section 6);
  • for package_groups: the packages they contain;
  • the labels and hashes of all dependencies, including deps that aspects might add (the same conservative treatment as --aspect_deps=conservative), and the toolchain types of exec groups and aspects;
  • for each toolchain_type: every toolchain registered for it in MODULE.bazel files. A toolchain() implemented in a fetched external repo is hashed by that repo's definition (repo rule, attribute values, files its label attributes point to such as patches) and the definitions of the repos it can see, without fetching it.

Dependencies through "nodep" attributes such as visibility don't count. A dependency that doesn't exist is hashed as <missing>, so creating it changes its dependents' hashes. Any other error, in a queried target or in one of its dependencies, is reported and fails the command.

--noimplicit_deps, --notool_deps and --aspect_deps values other than conservative are rejected, because they would drop dependencies from the hash. The flag is also rejected in genquery.

The hashes are unconfigured: they describe the target graph you see in bazel query. A select() contributes all of its branches, and --extra_toolchains and build options aren't seen. bazel cquery --experimental_generate_hashes hashes the configured graph instead. It prints <label> (<config>) <hash>, follows only the select() branches taken and the toolchains actually resolved, and includes the build options, so its hashes are only valid for the options they were computed with.

3 · Background

Skyframe in ten minutes

When you run bazel, the small C++ client talks to a long-lived Java server, which is why the second build in a session is so much faster than the first. The server keeps a huge in-memory graph of everything it has computed. That graph and the engine that maintains it are called Skyframe, and almost everything Bazel does (loading packages, reading files, analysing rules, running actions) is a node in it.

You already know the idea from actions: an action's output is reused as long as its inputs haven't changed. Skyframe applies the same rule to every piece of work.

SkyKeyThe name of a piece of work. "The file /src/app/main.go", "the package //app".
SkyValueThe result of that work. File metadata, a loaded package. Immutable, and compared with equals().
SkyFunctionThe code that turns a key into a value. It may ask Skyframe for other keys it needs.

Three properties matter for this page:

  1. Memoization. Once a key is computed, its value stays in the server's memory. The next command that asks for it gets it for free.
  2. Recorded dependencies and invalidation. When a SkyFunction asks for another key, Skyframe remembers the edge. Between commands, Bazel checks which files changed on disk and marks their nodes dirty. Everything that depends on them is then re-checked on the next command.
  3. Change pruning. When a dirty node is recomputed and its new value equals() the old one, its dependents are not recomputed. Touching a file without changing its contents doesn't cascade through the graph.

One more idiom shows up in every SkyFunction: if a value the function needs isn't computed yet, the function returns null. Skyframe computes the missing dependency and calls the function again from the top. That's why the code below is full of if (x == null) return null;.

Three existing nodes are central here:

  • FileStateValue: what a single stat() of a path found. For a regular file that includes its size and, when the filesystem can supply one cheaply, its content digest.
  • FileValue: a FileStateValue with symlinks resolved. This is what most code asks for when it wants to know about a file.
  • RepositoryDirectoryValue: the node that represents "this external repo has been fetched". It is recomputed when the repo is refetched.
4 · The new code

How the hashing is built

The branch adds four SkyFunctions and one plain Java class under src/main/java/com/google/devtools/build/lib/query2/query/hash/. BuiltinCommandModule registers the four functions with the server, and QueryCommand calls them when the flag is set.

PieceKindWhat it does
DirectTargetHashFunctionSkyFunctionGiven a label, returns the target's direct hash (everything about the target itself) and the sorted list of its dependency labels.
RepoContentDigestFunctionSkyFunctionGiven an external repo, returns one digest of all its files, or a marker meaning "hash this repo's files one by one" for the main repo and for local, configure and overridden repos.
SourceFileDigestFunctionSkyFunctionGiven a file path, returns its content digest and executable bit, or a marker for missing files, directories and special files. Used for files the repo digest doesn't cover.
RegisteredToolchainsByTypeFunctionSkyFunctionMaps each toolchain type to the toolchains registered for it in MODULE.bazel files.
TransitiveHashesPlain JavaWalks the graph, asks Skyframe for every direct hash, adds edges from toolchain types to their registered toolchains, then combines everything bottom-up into transitive hashes.

Why the transitive hash isn't a SkyFunction

The obvious design would have each target's SkyFunction ask for its deps' hashes and fold them in. That can't work here. The unconfigured target graph can contain cycles (for example, a toolchain whose tools depend back on something that uses the toolchain). In a real build, configuration transitions break those cycles, but query sees them, and Skyframe forbids cycles between nodes.

So the work is split. DirectTargetHashFunction never asks for another target's hash. It only returns the dep labels. TransitiveHashes then:

  1. Starts from the query results and requests their direct hashes from Skyframe in one batch.
  2. Collects the not-yet-seen dep labels into the next batch, and repeats until nothing new turns up. A toolchain_type gets extra edges to every toolchain registered for it. Each batch is one parallel Skyframe evaluation, and you see Hashing: visited N targets (depth D, …) in the progress bar.
  3. Runs Tarjan's algorithm over the collected graph. It finds the strongly connected components (each cycle, plus every target that isn't in a cycle as a component of one) and emits them leaves-first.
  4. For a target not in a cycle: hash = H(direct hash, [(dep label, dep hash) …]). Members of a cycle share one hash of all their direct hashes and edges, salted with each member's own label so they still get distinct hashes.

A dep that doesn't exist contributes a fixed <missing> marker, so a dep that later starts to exist still changes the hash. Other errors fail the command with "hashes of targets depending on them may be wrong".

Choosing between the repo digest and per-file digests

For a target in an external repo, DirectTargetHashFunction first asks RepoContentDigestFunction for that repo. If it returns a digest, a source file's direct hash uses the repo digest instead of its own content. A rule's same-package file deps are dropped from the walk and the repo digest is mixed into the rule's hash, which keeps the walk from visiting every file of large toolchain repos. Only when the repo function returns "use file digests" does the code fall back to SourceFileDigestFunction:

public SkyValue compute(SkyKey skyKey, Environment env) {
  RootedPath rootedPath = (RootedPath) skyKey.argument();
  FileValue fileValue = env.getValueOrThrow(FileValue.key(rootedPath), IOException.class);
  if (fileValue == null) return null;            // not computed yet; Skyframe will restart us
  if (!fileValue.exists()) return Value.MISSING;
  if (fileValue.isDirectory()) return Value.DIRECTORY;
  if (fileValue.isSpecialFile()) return Value.SPECIAL;
  // Prefer the digest already recorded in the file state …
  Path realPath = fileValue.realRootedPath(rootedPath).asPath();
  byte[] digest = fileValue.getDigest();
  if (digest == null) {
    // … otherwise read the file, going through the computed digest cache.
    digest = DigestUtils.manuallyComputeDigest(realPath, null);
  }
  return new Value(digest, realPath.isExecutable());
}

SourceFileDigestFunction.java (lightly trimmed)

This function depends only on the file's FileValue, so on a warm server it reruns exactly when Skyframe thinks the file changed.

5 · The other feature

The remote repo contents cache

From the user's side, --experimental_remote_repo_contents_cache stores the results of reproducible repository rules in your remote cache. When another machine (or a fresh output base) needs the same repo, Bazel skips running the repo rule. It also doesn't download the repo's files up front. They stay remote until something actually needs their bytes.

Inside, it works like this:

  1. Cache key. The repo rule's inputs (its attributes, the rule's code, and any files or environment variables it read) are hashed into the same "predeclared inputs hash" Bazel already uses to decide whether a repo needs refetching. That hash becomes the key of an Action Cache entry, the same kind of entry a cached build action uses.
  2. Cache entry. The entry's outputs are the repo's marker file and a Tree: the repo's full directory listing, with the size and content digest of every file. The Tree is metadata only. File contents live separately in the CAS, the cache's content-addressed blob store.
  3. On a hit. Bazel downloads the Tree, not the files, and injects it into an in-memory filesystem that sits over $(bazel info output_base)/external. That's RemoteExternalOverlayFileSystem. To the rest of Bazel the repo looks fully present: stat, readdir and symlinks all work.
  4. Lazy reads. Files are fetched only when their bytes are read. .bzl files and REPO.bazel are prefetched in bulk, because package loading will need them anyway. If a locally executed action needs the repo, the repo is written out to disk ("materialized").

The key detail for us: each file in the in-memory tree carries the digest from the Tree.

6 · The core of the answer

Where the two meet

Take a source file in a cached repo, @foo//:data.txt, and follow it through query --experimental_generate_hashes.

  1. Repo lookup. Loading @foo hits the cache, and the overlay filesystem now holds external/foo/ as remote files with known digests.

  2. Which path is taken. DirectTargetHashFunction asks RepoContentDigestFunction for @foo. Repos in the remote repo contents cache come from reproducible repo rules, which are never local or configure, so the function computes a whole-repo digest. SourceFileDigestFunction and the file's FileValue aren't used.

  3. The repo walk. The function lists the repo directory with readdir(Symlinks.NOFOLLOW), sorts the entries and recurses. For each entry it adds the relative path and type. Files add path.getDigest(); symlinks add their target, with absolute targets under the repo, external/, the workspace or the output base rewritten relative to those directories.

    case FILE -> {
  fp.addString("<file>");
  fp.addBytes(path.getDigest());
}

    RepoContentDigestFunction.java, addDirectory

    On the overlay filesystem, path.getDigest() is the override above, which returns the stored digest without downloading anything. The listing comes from the in-memory Tree too.

  4. The hash node. Back in DirectTargetHashFunction, data.txt hashes as its label, its kind and <repo contents> plus the repo digest. A rule in @foo with same-package file deps gets the repo digest the same way.

  5. Same answer as a local fetch. The overlay filesystem is built with the native filesystem's hash function (super(nativeFs.getDigestFunction())), the same function Bazel uses to hash files on disk. The digests in the Tree were computed from the same bytes you'd get from a local fetch. Executable bits are deliberately left out of the repo digest, because a locally fetched repo and one served lazily from the cache report them differently. So the hash comes out identical either way.

BUILD and .bzl files in the repo do still get read, but that's ordinary package loading, which any bazel query over @foo already does. --experimental_generate_hashes doesn't add downloads of its own.

Toolchain repos are cheaper still. When @foo is only reached as the implementation of a registered toolchain(), it isn't loaded at all. Its toolchain is hashed by the definitions of @foo and the repos it can see, so the repo is neither fetched nor looked up in the cache.
7 · Warm server

What happens across commands

The flag's help text promises that a warm server only recomputes what changed. For fetched external repos, RepoContentDigestFunction depends on the repo's RepositoryDirectoryValue. It reads the repo's files directly instead of through Skyframe, so it doesn't track each file. That keeps toolchain repos with hundreds of thousands of files from being checked on every command.

  • Repo refetched (its inputs changed, or you ran bazel fetch --force): the repo node is recomputed, and so is the repo digest. If the files are identical, the new value equals the old one and change pruning stops the cascade there.
  • The cache lost some of the repo's files: after the command, the overlay filesystem drops the repo from memory and invalidates its RepositoryDirectoryValue (RemoteExternalOverlayFileSystem.java:176-177), and the same chain follows on the next command.
  • Repo materialized to disk mid-session: the bytes don't change, so neither does the digest or the hash.
  • Edits by hand inside a fetched repo that don't cause a refetch aren't seen. This is a deliberate trade-off, listed in the flag's help text.
8 · Things to know

Edge cases

SituationWhat happensIs it a problem?
A file's bytes were evicted from the remote cacheHashing still succeeds, because only the stored digest is read.No. The hash still reflects the file's contents. A later build that needs the file will find the eviction and refetch the repo.
A cached repo is materialized onto a filesystem without fast digestsIf the repo digest is recomputed, getDigest() reads and hashes every file of the repo once.No for correctness: the digests and the hash are the same. It costs one full read of the repo per fetch.
A source label points at a directoryIn the main repo and in local or configure repos, it hashes as <directory> and the contents aren't walked. In fetched repos, the directory's contents are part of the repo digest.A limitation for the main repo and local repos only.
A file is a symlink inside the cached repoThe symlink isn't followed. Its target is hashed as a string, with absolute targets under the repo, external/, the workspace or the output base made relative. A symlink into the workspace also adds the content digest of the file it points to.No. Reproducible repos store relative symlinks, so the cache and a local fetch agree.
A file's executable bit changes in a fetched repoNot part of the repo digest.Deliberate: it keeps cache hits and local fetches consistent. Executable bits are hashed for the main repo and local repos.
9 · Gaps

What isn't tested yet

The branch has unit tests for the combining logic (TransitiveHashesTest: cycles, missing deps, determinism), Java integration tests (TransitiveHashesIntegrationTest, HashesOutputFormatterCallbackTest) and shell tests in bazel_query_test.sh and configured_query_test.sh. These cover external repo symlinks and executable bits. Nothing exercises --experimental_generate_hashes together with the remote repo contents cache.

Suggested test. In src/test/py/bazel/bzlmod/remote_repo_contents_cache_test.py, which already starts a remote cache: define a repo containing a source file, then run query --experimental_generate_hashes on it twice. First with a fresh output base (a cache miss, so the repo is fetched locally), then with another fresh output base (a cache hit). Check that the two hashes match, that the file was never downloaded on the second run, and that changing the file's contents changes the hash. Include an executable file and a symlink, since those are where a cache hit and a local fetch can differ.

Action Cache (AC)
The part of a remote cache that maps an action's key to its result. The repo contents cache reuses it with a synthetic "action" per repo.
CAS
Content-addressable storage: the part of a remote cache that stores file bytes, looked up by digest.
Change pruning
Skyframe skipping dependents when a recomputed value is equal to the old one.
Digest
A hash of a file's contents (SHA-256 by default, set by --digest_function).
Materialize
Write a remotely cached repo's files to the real disk.
Predeclared inputs hash
The hash of a repo rule's definition and attributes that Bazel uses to decide whether a repo needs refetching.
Repo digest
The single fingerprint RepoContentDigestFunction computes over a fetched repo's paths, file digests and symlink targets.
SCC
Strongly connected component: a set of targets that can all reach each other, which is how a cycle looks to a graph algorithm.
Tree
A remote-cache message describing a whole directory: names, sizes and digests of every file, without their contents.
