Medians of wall-clock time for the tool to produce its affected set for the head revision, with every tool's Bazel server warm and its base-revision state (hashes, worktree) already computed. For the hash-based tools this is hashing the head revision (plus bazel-diff's impacted-target diff); target-determinator inherently evaluates both revisions. Dependency and toolchain scenarios include fetching the changed external repositories. Each scenario also pays for reverting the previous one.



Method


    

  • Each scenario is one change committed on top of the same base revision of the fixture workspace (rules_cc + hermetic LLVM, rules_go, rules_python, rules_rs, rules_oci, rules_img, rules_apko, rules_distroless, rules_multitool, plus a custom rule and macro).
    • 

  • Ground truth: the workspace is built with an aspect that digests every top-level target's output files, runfiles and executable (contents and file modes), plus test-execution attributes (size, timeout, args, env, …). A target is affected when that digest changes, or when it is new.
    • 

  • Tools are scored on the targets the oracle digests (main-repository targets with outputs). Labels outside that set (source files, external repositories) are ignored.
    • 

  • Tools run unmodified with default options: the custom Bazel's query //... --generate_hashes, bazel-diff generate-hashes + get-impacted-targets, and target-determinator with -nocache_results. Each tool has its own output base.
